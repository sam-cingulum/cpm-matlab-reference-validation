# Genuine MATLAB R2026b read-only PLT call audit: negative result

Runner: https://github.com/sam-cingulum/cpm-matlab-reference-validation/actions/runs/43222091948

An x86-64 ELF `LD_AUDIT` module with `la_x86_64_gnu_pltenter` and `la_symbind64` was compiled and executed in the licensed MathWorks runner. It observed symbol bindings but **zero QR routine PLT entry events**. This does not establish that MATLAB did not call the routines: calls may be through non-PLT/direct/internal paths, the audited process may be a wrapper rather than the actual MATLAB engine, or the symbols may not have been reached via the instrumented PLT. The run exited 255, so the instrumented workflow **failed**. No private numerical working buffers or Householder coefficients were captured.

**New critical observation:** the six original MATLAB public QR outputs are *not all bitwise stable across the two instrumented runs* (43220857431 vs 43222091948). The second baseline n35 R22 differs by 1 ULP, outliers n29 R12 differs by 1 ULP, rescaled n29 R12 differs by 1 ULP, high-leverage n71 R12 differs by 2 ULP, heteroskedastic n71 R12 differs by 2 ULP. Do not assume these instrumented runs provide a valid bitwise oracle for native parity. Need an independent uninstrumented same-commit same-runner reference and explicit instrumentation noninterference gate. Runtime loader auditing may affect CPU dispatch or arithmetic; this is a hypothesis, not proven cause.

Next steps: run a clean licensed uninstrumented six-case control on identical workflow/environment, compare every R/h bit, capture actual executable process and loaded numerical modules without `LD_AUDIT`, then attempt a targeted function-boundary tracer in the actual MATLAB engine process with safe, strictly limited synthetic-data buffer access. No call-level evidence is certified yet.
